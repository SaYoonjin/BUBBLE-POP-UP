## 1. 실시간 게임 상태를 Redis Hash 기반으로 분리

### 상황

- 게임 영업 중에는 매장별 잔액, 재고, 판매가, 구매 커서, 누적 매출, 누적 비용, 고객 수, 액션 사용 여부가 계속 변합니다.
- 이 프로젝트는 실제 시간 `2분`을 게임 내 `10:00~22:00` 영업 시간으로 압축하고, `10초` 단위 tick으로 상태를 갱신합니다.
- 매 요청마다 DB에 상태를 저장하거나 처음부터 다시 계산하면, 영업 화면 조회가 늘어날수록 DB write 부하와 계산 비용이 커질 수 있었습니다.

근거 파일:
- `src/main/java/com/ssafy/S14P21A205/game/time/policy/GameTimePolicy.java`
- `src/main/java/com/ssafy/S14P21A205/game/day/service/GameDayStateService.java`
- `src/main/java/com/ssafy/S14P21A205/game/day/state/repository/GameDayStoreStateRedisRepository.java`

### 해결방법과 그렇게 생각한 이유

- 영업 중 live state는 Redis Hash에 저장하고, 하루가 끝난 뒤 확정 리포트만 DB에 저장하는 구조로 분리했습니다.
- Redis key는 `game:store:{storeId}:day:{day}:state` 형태로 잡고, tick 이력은 `game:store:{storeId}:day:{day}:tick_log`에 따로 남겼습니다.
- Redis Hash 필드를 `balance`, `stock`, `sale_price`, `purchase_cursor`, `tick_sales`, `cumulative_sales`, `cumulative_total_cost`, `last_calculated_at`처럼 잘게 나누어 일부 값만 갱신할 수 있게 했습니다.
- 상태 조회 시에는 마지막 계산 tick 이후부터 현재 tick까지만 진행하도록 구현했습니다. 즉, 매번 0번 tick부터 전체 재계산하지 않고 저장된 진행 지점에서 이어 계산합니다.
- Redis 상태가 없거나 시작 응답이 비어 있으면 `GameDayStartService.ensureCurrentDayState`로 현재 일차 상태를 복구하도록 해, 조회 API가 단순 실패로 끝나지 않게 했습니다.

이 방식을 선택한 이유는 영업 중 상태가 "영속 결과"라기보다 빠르게 변하는 "현재값"에 가깝기 때문입니다. Redis가 빠른 읽기/쓰기와 부분 갱신에 적합하고, DB는 확정 결과 저장에 집중하는 편이 책임 분리가 명확하다고 판단했습니다.

### 성과

- 하루 영업 `2분`, `10초` tick 기준 매장당 최대 `12개` 상태 갱신 단위를 Redis에서 처리하도록 구조화했습니다.
- Redis Hash에 live state 필드 `20개 이상`을 분리해 저장하고, tick별 로그까지 남길 수 있게 했습니다.
- DB는 일일 리포트와 최종 랭킹 같은 확정 데이터에 집중하고, 영업 중 잦은 상태 변경은 Redis로 흡수하는 기반을 만들었습니다.
- `GameDayStateServiceTests`, `GameDayStartServiceTests`, `GameDayStoreStateRedisRepositoryTests`에서 상태 초기화, Redis 저장/복구, tick 진행 흐름을 검증했습니다.

## 2. 시즌 TOP 랭킹 조회와 계산을 분리

### 상황

- 시즌 랭킹은 사용자가 자주 조회하는 데이터지만, 매 요청마다 모든 매장의 과거 리포트와 당일 실시간 상태를 합산하면 비용이 큽니다.
- 랭킹은 ROI 계산, 정렬, 동률 처리, 보상 포인트 계산까지 필요합니다.
- 사용자 요청 경로에 이 계산을 그대로 두면 랭킹 조회 API가 매장 수에 비례해 무거워질 수 있었습니다.

근거 파일:
- `src/main/java/com/ssafy/S14P21A205/game/season/scheduler/RealtimeSeasonRankingTickTask.java`
- `src/main/java/com/ssafy/S14P21A205/game/season/repository/SeasonRankingRedisRepository.java`
- `src/main/java/com/ssafy/S14P21A205/game/season/service/SeasonRankingService.java`

### 해결방법과 그렇게 생각한 이유

- 랭킹 계산은 `RealtimeSeasonRankingTickTask`가 주기적으로 수행하고, API는 Redis에 캐시된 TOP 10 결과를 조회하도록 분리했습니다.
- 과거 일차 매출/비용은 `DailyReport`에서 집계하고, 현재 일차의 누적 매출/비용은 Redis live state에서 가져와 합산했습니다.
- 정렬 기준은 `ROI desc -> userId asc -> storeId asc`로 고정했습니다. 같은 ROI일 때도 응답 순서가 흔들리지 않도록 하기 위해서입니다.
- 동률이면 같은 등수를 부여하고, 보상 포인트는 1등 `30`, 2등 `20`, 3등 `10`, 그 외 `5`로 계산했습니다.
- 진행 중 시즌이 없거나 매장이 없으면 랭킹 캐시를 삭제해 오래된 시즌의 랭킹이 노출되지 않도록 했습니다.

랭킹은 초 단위로 완전히 실시간일 필요보다 "주기적으로 최신화된 스냅샷"이 더 적합하다고 봤습니다. 같은 계산을 사용자 요청마다 반복하지 않고, 한 번 계산한 TOP 10을 여러 사용자가 공유하도록 만든 것이 핵심입니다.

### 성과

- 랭킹 조회 API의 비용을 "전체 매장 집계 + 정렬"에서 "Redis 캐시 조회" 중심으로 단순화했습니다.
- 확정 데이터(DB 리포트)와 실시간 데이터(Redis 누적값)를 합산해 현재 시즌의 진행 상황을 함께 반영했습니다.
- TOP 10 캐시, 동률 처리, 보상 포인트 산정, stale cache 삭제 정책을 포함한 랭킹 흐름을 구성했습니다.
- `RealtimeSeasonRankingTickTaskTests`, `SeasonRankingServiceTests`로 캐시 갱신, 정렬 안정성, 조회 정책을 검증했습니다.

## 3. 시즌 라이프사이클과 게임 시간을 정책 객체로 통합

### 상황

- 게임은 입지 선택, 영업 준비, 영업 중, 일일 리포트, 시즌 요약, 다음 시즌 대기 상태를 순서대로 가집니다.
- 주문 가능 여부, 액션 가능 여부, 현재 일차, 현재 tick, 화면에 보여줄 게임 시간이 모두 시간 정책에 의존합니다.
- 시간 계산이 API마다 흩어지면 "어떤 API는 영업 중이라고 보고, 다른 API는 준비 중이라고 보는" 불일치가 생길 수 있었습니다.

근거 파일:
- `src/main/java/com/ssafy/S14P21A205/game/time/policy/GameTimePolicy.java`
- `src/main/java/com/ssafy/S14P21A205/game/time/service/SeasonTimelineService.java`
- `src/main/java/com/ssafy/S14P21A205/game/season/service/CurrentSeasonTimeService.java`
- `src/main/java/com/ssafy/S14P21A205/config/ClockConfig.java`

### 해결방법과 그렇게 생각한 이유

- 시간 계산을 `GameTimePolicy`와 `SeasonTimelineService`로 모았습니다.
- 정책 값은 입지 선택 `2분`, 영업 준비 `50초`, 영업 `2분`, 리포트 `10초`, 시즌 요약 `2분`, 다음 시즌 대기 `5분`으로 명시했습니다.
- 실제 영업 시간은 `10:00~22:00`로 표현하되, 실제 `2분`을 게임 내 `12시간`으로 매핑했습니다.
- `resolveSeasonPhase`, `resolveCurrentDay`, `resolveGameTime`, `resolveTick`, `resolveRemainingPhaseSeconds`처럼 API들이 필요한 시간 판단을 한 정책 객체에서 가져가게 했습니다.
- `Clock`을 Bean으로 주입해 테스트에서 특정 시각을 고정할 수 있게 했습니다.

이 구조를 선택한 이유는 시간 정책이 게임 전체의 공통 언어이기 때문입니다. 정책 객체 하나를 기준으로 두면 시즌/주문/액션/랭킹/마감 스케줄러가 같은 시각 판단을 공유할 수 있습니다.

### 성과

- 시즌 1개를 `7일` 기준으로 운영할 때 입지 선택, 7일치 영업 루프, 시즌 요약, 다음 시즌 대기까지 일관되게 계산할 수 있게 했습니다.
- 영업 `2분`을 `10초` tick `12개`로 나누어 상태 갱신, 랭킹 갱신, 일차 마감 판단의 기준을 통일했습니다.
- `GameTimePolicyTests`, `CurrentSeasonTimeServiceTests`, `ClockConfigTests`로 시간 경계값과 테스트 가능성을 확보했습니다.

## 4. 시즌 시작 전 Spark ETL 데이터 정합성 검증

### 상황

- 게임 시즌은 유동인구, 교통, 날씨, 이벤트, 뉴스 데이터에 의존합니다.
- 특정 지역만 데이터 일자가 부족하거나, 교통 데이터와 유동인구 데이터의 배치가 다르면 시즌 결과가 불공정해질 수 있습니다.
- 데이터가 단순히 "존재한다"는 것만으로는 모든 지역이 같은 기준의 데이터를 쓰는지 보장할 수 없었습니다.

근거 파일:
- `src/main/java/com/ssafy/S14P21A205/game/season/service/SeasonLifecycleService.java`
- `src/main/java/com/ssafy/S14P21A205/game/scheduler/SparkEtlScheduler.java`
- `spark/jobs/etl_population_score.py`
- `spark/jobs/etl_traffic_score.py`
- `spark/jobs/list_available_dates.py`

### 해결방법과 그렇게 생각한 이유

- 시즌 시작 전에 Spark ETL을 실행하고, 시작 가능한 `sourceBatchKey`를 확인한 뒤 시즌을 시작하도록 했습니다.
- 유동인구와 교통 데이터 모두 단일 batch key를 가져야 하고, 모든 지역이 동일한 날짜 목록을 가져야 시작 가능하도록 검증했습니다.
- 시즌 총 일수만큼 정확히 source day가 있어야 하므로, `ensureExactSourceDays`, `ensureSameSourceDates`, `ensureSourceBatchKey` 같은 검증 로직을 두었습니다.
- Spark ETL과 뉴스 생성 준비는 `@Transactional(propagation = NOT_SUPPORTED)`로 트랜잭션 밖에서 수행했습니다. Spark 쪽 DDL/외부 프로세스 실행이 Spring 트랜잭션과 섞이면 snapshot이나 재진입 문제가 생길 수 있다고 봤기 때문입니다.
- 시즌 준비 과정은 `newsReportRepository.existsBySeasonId`로 중복 실행을 막았습니다.

이 방식은 게임 결과의 공정성을 데이터 준비 단계에서 지키기 위한 선택입니다. 시즌이 시작된 뒤 오류를 복구하기보다, 시작 조건 자체를 엄격히 검증하는 쪽이 사용자 경험과 운영 안정성에 유리하다고 판단했습니다.

### 성과

- 시즌 시작 조건을 `배치키 일치 + 지역별 날짜 정렬 + 시즌 일수 일치`로 명확히 정의했습니다.
- Spark job `11개`로 인구, 교통, 뉴스, 검증, 날짜 조회 흐름을 구성했습니다.
- ETL/뉴스 준비를 트랜잭션 밖으로 분리해 DB 트랜잭션과 외부 프로세스 실행의 결합도를 낮췄습니다.
- 데이터 불일치로 인한 런타임 장애를 시즌 시작 전 대기 상태로 흡수할 수 있는 구조를 만들었습니다.

## 5. 일일 마감 작업을 멱등 Job + Retry 구조로 고도화

### 상황

- 하루 영업이 끝나면 모든 매장의 일일 리포트를 저장하고, 마지막 날에는 최종 랭킹도 확정해야 합니다.
- 스케줄러가 중복 실행되거나 서버가 처리 중 재시작되면 같은 일차 마감이 두 번 실행될 수 있습니다.
- 반대로 마감 중 일부 저장이 실패하면 다음 일차 진행과 랭킹 확정이 꼬일 수 있었습니다.

근거 파일:
- `src/main/java/com/ssafy/S14P21A205/game/day/service/SeasonDayClosingService.java`
- `src/main/java/com/ssafy/S14P21A205/game/day/service/DayClosingJobService.java`
- `src/main/java/com/ssafy/S14P21A205/game/day/entity/DayClosingJob.java`
- `src/main/resources/db/migration/V3__add_closing_idempotency_constraints.sql`
- `src/main/resources/db/migration/V4__create_day_closing_job.sql`

### 해결방법과 그렇게 생각한 이유

- `day_closing_job` 테이블을 만들고, `season_id + day`에 unique constraint를 걸어 일차별 마감 작업을 하나만 등록하도록 했습니다.
- 마감 실행 전에는 `findBySeasonIdAndDayForUpdate`로 Job row를 잠그고, claim 가능한 상태일 때만 `PROCESSING`으로 전환했습니다.
- 처리 중 작업이 영원히 묶이지 않도록 `PROCESSING_LEASE`를 `1분`으로 두고, 실패하면 `next_retry_at`을 갱신해 재시도 대상으로 돌렸습니다.
- 재시도 지연은 `10초`부터 시작해 최대 `300초`까지 증가하도록 했습니다.
- `daily_report`에는 `store_id + day`, 최종 랭킹에는 `store_id` unique constraint를 추가해 중복 저장을 DB 제약으로 한 번 더 방어했습니다.
- 중복 마감이 들어와도 unique constraint 위반이면 "이미 다른 작업이 저장했다"고 보고 넘어가도록 처리했습니다.

이 방식을 선택한 이유는 마감 처리가 비즈니스 정산의 기준점이기 때문입니다. 애플리케이션 레벨 플래그만으로는 동시 실행과 재시작 상황을 완전히 막기 어렵기 때문에, DB unique constraint와 row lock을 마지막 방어선으로 사용했습니다.

### 성과

- 일차 마감 작업의 유일성 기준을 `season_id + day`로 명확히 정의했습니다.
- 마감 작업 상태를 `PENDING`, `PROCESSING`, `COMPLETED` 중심으로 관리하고, 실패 시 retry 대상이 되도록 만들었습니다.
- 중복 실행 방어를 서비스 로직과 DB 제약 양쪽에서 처리해 정산 데이터 중복 저장 가능성을 낮췄습니다.
- `DayClosingJobServiceTests`, `SeasonDayClosingServiceTests`, `SeasonDayClosingRetrySchedulerTests`로 claim, retry, 중복 실행 방어 흐름을 검증했습니다.

## 6. 핵심 정산과 뉴스 생성을 분리해 마감 안정성 확보

### 상황

- 일일 마감에는 리포트 저장, 최종 랭킹 저장, Redis 기반 순위 집계, 마감 뉴스 생성이 함께 필요합니다.
- 뉴스 생성이나 랭킹 보조 집계가 느려지거나 실패하면, 핵심 정산까지 지연될 위험이 있었습니다.
- 사용자가 다음 일차로 넘어가기 위해 반드시 필요한 것은 리포트와 최종 랭킹이고, 뉴스는 조금 늦어져도 되는 부가 기능이었습니다.

근거 파일:

### 해결방법과 그렇게 생각한 이유

- `closeCoreData`에서 일일 리포트와 최종 랭킹을 먼저 동기로 확정했습니다.
- Redis 기반 순위/뉴스 갱신은 `CompletableFuture.runAsync`와 `dayClosingExecutor`를 사용해 별도 작업으로 분리했습니다.
- 비동기 뉴스 작업에서 예외가 나도 마감 Job 완료 상태가 깨지지 않도록 try/catch로 격리했습니다.
- 마지막 날이면 `SeasonFinalRankingService.saveFinalRankings`를 동기로 실행해 시즌 결과 확정을 우선했습니다.

정산 데이터는 다음 게임 상태의 기준이므로 반드시 순서와 성공 여부를 관리해야 합니다. 반면 뉴스는 사용자 경험을 풍부하게 하는 기능이지만, 핵심 정산을 막을 정도로 강한 의존성을 둘 필요는 없다고 판단했습니다.

### 성과

- 일일 리포트 저장과 최종 랭킹 확정은 핵심 경로에서 보장하고, 뉴스 생성 실패가 마감 전체 실패로 전파되지 않도록 했습니다.
- 마감 로직의 책임을 `정산 확정`과 `부가 집계/뉴스 생성`으로 분리했습니다.
- 운영 중 외부/부가 작업이 불안정해도 게임 시즌 진행이 막히지 않는 구조를 만들었습니다.

## 9. OAuth2 + JWT + Redis Refresh Token 회전 구조

### 상황

- 프론트엔드와 백엔드가 분리된 환경에서 Google/SSAFY OAuth 로그인을 지원해야 했습니다.
- API는 stateless JWT로 보호하되, refresh token은 로그아웃과 재발급 시 서버 측에서 폐기 가능해야 했습니다.
- OAuth redirect 과정에서는 임의 URL로 이동하는 open redirect 위험도 고려해야 했습니다.

근거 파일:
- `src/main/java/com/ssafy/S14P21A205/config/SecurityConfig.java`
- `src/main/java/com/ssafy/S14P21A205/auth/service/AuthService.java`
- `src/main/java/com/ssafy/S14P21A205/auth/service/JwtTokenService.java`
- `src/main/java/com/ssafy/S14P21A205/security/handler/AuthLoginSuccessHandler.java`
- `src/main/java/com/ssafy/S14P21A205/auth/service/AuthRedirectService.java`

### 해결방법과 그렇게 생각한 이유

- OAuth 로그인 성공 후 자체 access token과 refresh token을 발급했습니다.
- access token 기본 TTL은 `30분`, refresh token 기본 TTL은 `14일`로 설정했습니다.
- refresh token에는 `jti`를 넣고, Redis에는 `auth:refresh:{jti}` key로 사용자 ID를 저장했습니다.
- refresh 요청이 들어오면 JWT 자체 검증뿐 아니라 Redis에 저장된 `jti`와 subject가 일치하는지 확인했습니다.
- 검증 성공 후 기존 refresh token key를 삭제하고 새 refresh token을 발급하는 회전 방식을 적용했습니다.
- refresh token은 HttpOnly cookie로 내려 JavaScript 접근을 제한하고, access token은 redirect fragment에 담아 callback 페이지에서 처리하도록 했습니다.
- redirect URL은 `AuthRedirectService.isSafeRedirect`로 검증한 뒤 사용했습니다.

이 방식을 선택한 이유는 JWT의 stateless 장점과 refresh token 폐기 가능성을 동시에 가져가기 위해서입니다. access token은 짧게 가져가고, refresh token은 Redis에 저장된 jti를 통해 서버 측 무효화를 가능하게 했습니다.

### 성과

- OAuth2 로그인, JWT 발급, refresh token 회전, logout 시 Redis key 삭제 흐름을 구성했습니다.
- Google과 SSAFY provider를 모두 고려하되, SSAFY 설정이 없으면 명확히 invalid input으로 처리하도록 했습니다.
- `SecurityConfigTests`, `SsafyOAuthSettingsTests`에서 보안 설정과 OAuth provider 설정을 검증했습니다.

## 12. Flyway와 profile 분리로 운영 DB 변경 안정화

### 상황

- 운영 DB를 Hibernate `ddl-auto=create/update`에 맡기면 데이터 손실이나 의도치 않은 스키마 변경 위험이 큽니다.
- 동시에 로컬 개발에서는 초기 데이터와 편의 설정이 필요했습니다.
- 일일 마감 멱등성처럼 unique constraint나 job table이 필요한 변경은 적용 순서가 중요했습니다.

근거 파일:
- `src/main/resources/application-local.yml`
- `src/main/resources/application-prod.yml`
- `src/main/resources/db/migration/V1__drop_pending_location_reserved_day.sql`
- `src/main/resources/db/migration/V2__drop_reputation_score_from_season_ranking_record.sql`
- `src/main/resources/db/migration/V3__add_closing_idempotency_constraints.sql`
- `src/main/resources/db/migration/V4__create_day_closing_job.sql`

### 해결방법과 그렇게 생각한 이유

- local/prod profile을 분리했습니다.
- prod에서는 Flyway migration을 활성화하고 Hibernate는 `ddl-auto=validate`로 설정했습니다.
- migration 파일로 스키마 변경 이력을 남기고, 운영 DB는 애플리케이션 시작 시 엔티티와 스키마가 맞는지만 검증하도록 했습니다.
- 일일 마감 중복 방어를 위해 `daily_report`, `season_ranking_record`, `day_closing_job`에 필요한 unique constraint와 index를 migration으로 관리했습니다.

### 성과

## 15. ControllerDoc 패턴과 Swagger 로그인 오버레이로 API 협업성 개선

### 상황

- 프론트엔드와 분리된 백엔드에서는 API 스펙, 인증 방식, 실패 응답을 문서에서 바로 확인할 수 있어야 합니다.
- 컨트롤러 메서드에 Swagger 설명, 응답 코드, 보안 요구사항까지 모두 넣으면 실제 HTTP 처리 코드가 문서 어노테이션에 묻히기 쉽습니다.
- JWT 인증 API는 Swagger에서 직접 테스트하기 번거로워, 개발자가 매번 외부 로그인 플로우와 토큰 복사를 반복해야 하는 불편도 있었습니다.

근거 파일:
- `src/main/java/com/ssafy/S14P21A205/auth/controller/AuthController.java`
- `src/main/java/com/ssafy/S14P21A205/auth/controller/AuthControllerDoc.java`
- `src/main/java/com/ssafy/S14P21A205/game/day/controller/GameDayController.java`
- `src/main/java/com/ssafy/S14P21A205/game/day/controller/GameDayControllerDoc.java`
- `src/main/java/com/ssafy/S14P21A205/config/OpenApiConfig.java`

### 해결방법과 그렇게 생각한 이유

- `*Controller`는 `@GetMapping`, `@PostMapping`, service 호출, `ResponseEntity` 반환에 집중하도록 했습니다.
- Swagger 문서는 `*ControllerDoc` 인터페이스로 분리하고, 컨트롤러가 해당 인터페이스를 구현하도록 구성했습니다.
- `@Operation`, `@ApiResponses`, `@SecurityRequirement`, `@Schema`를 문서 인터페이스에 배치해 API 설명과 구현 코드를 분리했습니다.
- `OpenApiConfig`에서 `bearerAuth` 보안 스키마를 등록했습니다.
- `SwaggerUiLoginOverlayConfig`에서 Swagger index HTML에 Google/SSAFY 로그인, 내 정보 조회, 토큰 재발급, 로그아웃 버튼을 주입했습니다.
- Swagger 로그인 오버레이는 access token을 localStorage에 저장하고 `preauthorizeApiKey("bearerAuth", accessToken)`로 Try it out에 자동 반영하도록 했습니다.

이 구조를 선택한 이유는 API 문서가 협업 산출물이면서 동시에 구현 코드의 가독성을 해치지 않아야 하기 때문입니다. 컨트롤러는 얇게 유지하고, 문서와 인증 테스트 편의성을 별도로 구성하면 프론트엔드와 백엔드가 같은 스펙을 기준으로 빠르게 검증할 수 있습니다.

### 성과

- `ControllerDoc` 인터페이스 `9개`로 도메인별 API 문서 구조를 분리했습니다.
- 인증이 필요한 API에는 Swagger security requirement를 명시해 문서에서 보호 API 여부를 확인할 수 있게 했습니다.
- Swagger UI 안에서 OAuth 로그인부터 JWT 적용, refresh, logout까지 확인할 수 있어 API 수동 테스트 흐름을 줄였습니다.
- 지원서에서는 "API 구현뿐 아니라 프론트엔드 협업과 테스트 편의성을 고려해 문서화 구조를 설계했다"는 개발 역량 사례로 사용할 수 있습니다.

- JWT secret 길이, redirect allow-list, HttpOnly refresh cookie, `Clock` 주입처럼 보안과 테스트 가능성을 함께 고려해야 했습니다.

### 보안과 API 품질
